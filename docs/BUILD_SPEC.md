# Cabinet Design & CAD Handoff Platform: Build Spec

Version 0.1 · October 26, 2026 · Status: Draft for review

---

## 1. Overview

This platform lets a cabinet business run sales, customer intake, and design in its own software, then hand finished designs to CAD/CAM software for engineering and production without re-entering anything by hand.

Designers capture the room and the customer's selections. An AI proposes a layout using the business's design rules. The designer reviews and adjusts it in a visual editor. The approved design is translated into Cabinet Vision's ORDX import format. After Cabinet Vision engineers the job, the platform reads the result back and checks that everything arrived as intended.

The platform does not engineer cabinets. It describes what goes where, at what size, with which selections. Cabinet Vision remains responsible for how each cabinet is built: parts, joinery, materials, and machining.

**Goals**

| ID | Goal |
|---|---|
| G1 | Eliminate manual re-entry of designs into CAD software. |
| G2 | Produce a reviewable first-draft design automatically from intake data and design rules. |
| G3 | Catch errors between design and CAD before anything is cut. |
| G4 | Keep the core product independent of any single CAD vendor, so Mozaik or others can be added later without rework. |
| G5 | Fail loudly. A job that cannot be translated exactly is blocked, never sent with guesses. |

---

## 2. Scope

**In scope for v1:** project and customer tracking, room capture, a visual design editor, an AI design assistant, a product catalog with buildability rules, a Cabinet Vision adapter (ORDX writer, reader, and catalog sync), a job comparer, and a translator test library with a correction workflow.

**Out of scope for v1:** parametric engineering of cabinets, CNC output, cutlists, or machining generated by this platform; a Mozaik push integration (reading Mozaik data is a possible later phase); and photorealistic rendering. The editor needs to look right and be dimensionally exact, not render like a showroom.

---

## 3. End-to-End Workflow

| Stage | Performed by | Input | Output |
|---|---|---|---|
| 1. Intake | Salesperson or designer in the Projects module | Customer details, project info | Project record with a job ID |
| 2. Room capture | Designer in the Designer module | Measurements, openings, obstacles, utilities | Room geometry in the master copy |
| 3. Selections | Designer | Door style, finish, hardware, construction preferences | Job-level and item-level selections in the master copy |
| 4. AI draft | AI Design module | Master copy (room and selections), shop design rules, product catalog | Proposed layout written to the master copy, marked as a draft |
| 5. Review and edit | Designer in the visual editor | AI draft | Revised master copy |
| 6. Ready-to-send gate | Core, Catalog, and Adapter checks | Master copy | Pass, or a list of blocking issues |
| 7. Translate | Cabinet Vision adapter | Approved master copy | ORDX file |
| 8. Engineer | Shop staff in Cabinet Vision | ORDX file | Engineered job (parts, machining via S2M) |
| 9. Read back | Cabinet Vision adapter (reader) | Cabinet Vision export, database, or reports | Returned job converted to master copy format |
| 10. Compare | Comparer module | Sent master copy and returned master copy | Discrepancy report |
| 11. Release | Shop staff | Clean comparison and human review | Job released to production |

Any correction made in Cabinet Vision after import that reflects a translation error is captured as a test case (Section 8).

## 4. Architecture Principles

| ID | Principle | What it means in practice |
|---|---|---|
| P1 | The master copy is the single source of truth | Every job is described in our own format. The editor, AI, pricing, checks, and translators all read and write this format and nothing else. |
| P2 | Dependencies point inward | Core and Catalog depend on nothing else. Designer, AI Design, adapters, and Projects depend on Core and Catalog, never the reverse. The words "Cabinet Vision" must not appear outside the Cabinet Vision adapter. |
| P3 | Data over code | Size ranges, option rules, mappings, and design rules are stored as data that the system checks against, not hard-coded logic. |
| P4 | Fail closed | Any missing, unmapped, out-of-range, or ambiguous value blocks the operation with a clear message. No component guesses or falls back to a default silently. |
| P5 | AI builds the tools; the tools run deterministically | AI is used to write and improve translators and to draft designs for human review. Translation itself is ordinary code: the same input always produces the same output. |
| P6 | The picture renders from the data | The visual editor draws only from the master copy. What the designer sees is exactly what will be translated. |
| P7 | Verify independently | Read-back checks use a source independent of our own translator's assumptions wherever possible. |

## 5. Module Specifications

### 5.1 Module map

| Module | Responsibility | May depend on | Must not depend on |
|---|---|---|---|
| Core | Master copy format, units, geometry, layout checks | Nothing | Everything else |
| Product Catalog | Our items, options, size ranges, buildability rules | Core | Adapters, Designer, AI |
| Shop Settings | Per-shop design rules, defaults, preferences | Core, Catalog | Adapters |
| Visual Library | 3D models, textures, and icons for display | Catalog (item IDs only) | Adapters |
| Designer | Room capture, visual editing, rendering | Core, Catalog, Shop Settings, Visual Library | Adapters |
| AI Design | Drafts layouts into the master copy | Core, Catalog, Shop Settings | Designer UI, Adapters |
| Cabinet Vision Adapter | Mapping, ORDX writer, reader, catalog sync, preflight | Core, Catalog | Designer, AI, Projects |
| Comparer | Compares two master copies | Core | Adapters |
| Projects & Sales | Customers, quotes, status, pricing | Core, Catalog (links to jobs by job ID) | Adapters, design internals |
| Translator Test Library | Golden test cases and regression runs | Core, each adapter | Designer, AI |

### 5.2 Core

Core defines the master copy format (Section 6), a single internal unit system, and generic geometry. It also owns layout checks: rules that apply regardless of catalog or CAD software, such as overlaps, items beyond walls, door swing and clearance conflicts, and blocked openings. Core exposes a validation interface that other modules extend with their own checks, so the ready-to-send gate (Section 7) can run every module's checks without Core knowing about them.

### 5.3 Product Catalog

The catalog is our own list of what can be designed: item types (base, wall, tall, filler, panel, molding, and so on), their allowed width, height, and depth ranges and increments, the options each item supports, which selections are required, and which option combinations are invalid. Every catalog record has a stable ID that never changes once used in a job, and a version history so a job can be checked against the catalog as it was when designed.

The catalog is shop-agnostic in structure but populated per shop. A shop's catalog is created by mapping its Cabinet Vision library into our items through the adapter's catalog sync (5.8), then curated. Items with no clean mapping are either excluded from the editor or flagged as "manual work required."

Pricing reads from the catalog, never from Cabinet Vision.

### 5.4 Shop Settings

Shop Settings holds each shop's design rules (for example, sink base centered on the window, minimum filler beside appliances, preferred upper height), default selections, and preferences. Design rules are stored as structured data with a plain-language description, so designers can read them and the AI can apply them.

### 5.5 Visual Library

The visual library holds how things look: models, textures, door style previews, and icons, linked to catalog items by ID. It holds no dimensions or rules. Visual approximation is acceptable here; dimensional accuracy comes from the master copy.

### 5.6 Designer

The Designer covers room capture (walls, angles, ceiling height, openings, obstacles, utilities) and visual editing of the layout. It offers only catalog items available to the current shop, constrains sizes to allowed ranges as the designer edits, shows validation issues live, and renders exclusively from the master copy. It displays AI drafts as editable designs and marks which items the AI placed versus which the designer changed.

### 5.7 AI Design

AI Design takes the master copy (room and selections), the shop's design rules, and the shop's catalog, and writes a proposed layout into the master copy as a draft. It may only use catalog items and must produce output that passes the same validation as a human design; drafts that fail are returned with their issues listed rather than hidden. It records a short explanation of its key decisions for the designer to review. A designer must approve before a draft can pass the ready-to-send gate.

### 5.8 Cabinet Vision Adapter

This is the only module that knows Cabinet Vision exists. It contains:

**Mapping tables.** Map our catalog item plus option combinations to the shop's Cabinet Vision catalog entries and parameters. Each mapping records the Cabinet Vision catalog version it was verified against.

**Catalog sync.** Imports the shop's Cabinet Vision library export, detects added, removed, or changed entries, and flags any mapping that no longer matches. Flagged mappings block sending for affected items until resolved.

**Preflight checks.** Confirms every item and option in the job has a current, verified mapping and that every field ORDX requires is present.

**ORDX writer.** Converts an approved master copy into an ORDX file. It must be deterministic and must refuse to write a file if any value is missing or unmapped.

**Reader.** Pulls the engineered job back out of Cabinet Vision and converts it into master copy format. Candidate sources are ORDX export, the Cabinet Vision SQL database, and report exports; the best source is decided during discovery (Phase 0).

**Independent verification source.** At least one read-back path must come from Cabinet Vision's own engineered output (for example, a cutlist or materials report) rather than only an ORDX round trip, so translator and reader cannot share an unnoticed misunderstanding.

### 5.9 Comparer

The Comparer takes the sent master copy and the returned master copy and reports differences: missing or extra items, dimension differences beyond a strict tolerance, position differences, and selection mismatches. It knows nothing about any CAD software and works unchanged for any future adapter.

### 5.10 Projects & Sales

Projects & Sales covers customers, leads, quotes, project status, milestones, and scheduling. It links to designs by job ID only and does not store design data. Quotes are priced from the catalog and the current master copy.

### 5.11 Future: Mozaik Adapter

Mozaik can export job data to a SQLite database, so a Mozaik reader is feasible. No supported whole-job import path is currently known, so a Mozaik adapter would initially support read-back and comparison only, with designers placing cabinets in Mozaik by hand from a generated build sheet. Thanks to P1 and P2, adding it requires no changes outside the new adapter.

## 6. Master Copy Data Model

All lengths are stored as exact integers in one internal base unit, chosen so every real-world increment the shop uses is a whole number (for imperial shops, a candidate is 1/64 inch). Conversion happens only at the edges: the editor's display and the adapters. Angles use a single convention, documented in Core.

**Job**

| Field | Description |
|---|---|
| job_id | Stable unique ID, shared with Projects & Sales |
| shop_id | The shop this job belongs to |
| catalog_version | Catalog version the design was validated against |
| status | draft, ai_draft, in_review, approved, sent, returned, verified, released |
| job_selections | Default selections for the whole job (door style, finish, hardware, construction) |
| rooms | List of Room |
| history | Who changed what and when, including AI versus designer edits |

**Room**

| Field | Description |
|---|---|
| room_id | Stable ID within the job |
| name | For example, "Kitchen" |
| ceiling_height | Base units |
| walls | Ordered list of Wall |
| room_selections | Overrides of job-level selections |
| items | List of PlacedItem |

**Wall**

| Field | Description |
|---|---|
| wall_id | Stable ID |
| start_point, end_point | Base units, in room coordinates |
| height, thickness | Base units |
| openings | Windows, doors, and passthroughs with position, width, height, and sill height |
| obstacles | Outlets, switches, plumbing, vents, soffits, and so on, with position and size |

**PlacedItem**

| Field | Description |
|---|---|
| item_instance_id | Stable ID within the job |
| catalog_item_id | Our catalog ID, never a CAD-specific code |
| width, height, depth | Base units, within catalog ranges |
| position | Wall reference plus offset along the wall and elevation, or room coordinates for islands |
| rotation | Per Core's angle convention |
| item_selections | Overrides of room or job selections |
| modifications | Catalog-defined modifications only (for example, scribe, end panel); free-form modifications are not allowed |
| origin | ai or designer, plus last editor |
| notes | Free text for the shop; never used for translation |

Effective selections for an item are resolved in order: item, then room, then job. The resolved values, not the inheritance chain, are what validation and translation check.

## 7. Validation and the Ready-to-Send Gate

A job can be translated only when every check below passes and a designer has approved it. Each check reports which item failed and why, in plain language.

| Layer | Owner | Example checks | Severity |
|---|---|---|---|
| Layout | Core | Items overlap; item extends past a wall; item blocks an opening; door or drawer swing conflicts; clearance below minimum | Block (some clearance rules may be warnings per shop setting) |
| Buildability | Catalog | Dimension outside the item's allowed range or increment; invalid option combination; required selection missing; item not available to this shop | Block |
| Design rules | Shop Settings | Shop-specific preferences not met | Warn by default; each shop can promote rules to Block |
| Translation preflight | CV Adapter | Item or option has no mapping; mapping is stale against the latest catalog sync; a field ORDX requires is empty | Block |
| Approval | Designer | AI draft not yet reviewed and approved by a designer | Block |

## 8. Translator Development and Correction Loop

**Discovery.** Collect a varied set of real jobs from Cabinet Vision, each with its ORDX export and its engineered output (cutlist or report). Include unusual jobs: angled walls, corners, islands, fillers, end panels, and modified cabinets. AI analyzes the samples and produces a written ORDX format reference, which is reviewed by someone who knows Cabinet Vision well. Anything the samples don't explain is listed as an open question rather than guessed.

**Building.** AI writes the ORDX writer and the reader from the format reference. Both are ordinary code, reviewed and version-controlled.

**Golden test library.** Each test case contains a master copy, the expected ORDX output, and the expected engineered result from Cabinet Vision. The library starts with the discovery samples and grows with every correction.

**Correction workflow.** When a translation error is found (by the Comparer, a designer, or shop staff), the job, what was sent, what came back, and the correct result are saved as a new test case. AI proposes a fix to the code or the mapping. The full test library runs against the fix, and the fix ships only if every test passes. Each fix is logged with its cause.

**Cabinet Vision updates.** Before a shop uses a new Cabinet Vision version in production, the full test library is run against it. Differences block the upgrade for that shop until resolved.

**What AI does not do.** AI does not translate jobs at runtime, does not modify mappings without review, and does not resolve open questions about Cabinet Vision behavior by assumption.

## 9. Silent-Failure Safeguards

| Risk | How it fails silently | Safeguard | Owner |
|---|---|---|---|
| Cabinet Vision defaults | A missing or unrecognized value is replaced with a default on import | Writer requires every field and refuses unmapped values; Comparer checks selections after import | CV Adapter, Comparer |
| Stale mappings | Shop changes its Cabinet Vision library; mappings point to old entries | Catalog sync on a schedule and before sending; stale mappings block affected items | CV Adapter |
| Hard-coded rules drifting | Size ranges in code no longer match the real catalog | All ranges and rules stored as catalog data with version history | Catalog |
| Shared blind spots | Writer and reader share the same wrong assumption, so round-trip checks pass | Independent verification against Cabinet Vision's own engineered output; human spot checks in early phases | CV Adapter |
| Picture and data disagree | Editor shows something different from what will be translated | Editor renders only from the master copy | Designer |
| Unit and rounding errors | Small dimension shifts during conversion | Integer base units; conversion only at the edges; Comparer uses strict tolerances | Core, Comparer |
| CAD version changes | New Cabinet Vision version reads ORDX differently | Full test library run before each upgrade | Test Library |
| Reviewer complacency | Designers approve AI drafts without checking | AI-placed items visibly marked; key decisions explained; validation runs on every draft | Designer, AI Design |
| Untested edge cases | Situations not in the test library behave unpredictably | Items outside tested coverage are flagged for manual review until covered | CV Adapter, Test Library |

## 10. Build Phases

The riskiest unknown (whether translation works reliably) is tested before the most expensive pieces (the visual editor and AI) are built.

| Phase | Work | Exit criteria |
|---|---|---|
| 0. Discovery | Collect jobs, ORDX exports, engineered outputs, and the shop's catalog export; write the ORDX format reference; choose the read-back source | Format reference reviewed; open questions listed; read-back source chosen |
| 1. Proof slice | Define the master copy (Section 6); hand-write a few master copies for one wall of base cabinets in one door style; build a minimal writer; import into Cabinet Vision | Go/no-go: test jobs import correctly with no manual fixes. If not, stop and reassess. |
| 2. Read-back and compare | Build the reader, the independent verification path, and the Comparer | Proof-slice jobs round-trip with zero unexplained discrepancies |
| 3. Expand coverage | Add uppers, talls, corners, fillers, panels, islands, more styles and options; grow the test library | Agreed coverage list passes; every fix has a test case |
| 4. Catalog and shop onboarding | Product Catalog, catalog sync, mapping tools, Shop Settings | A shop's catalog can be mapped and kept in sync; stale mappings are detected |
| 5. Designer | Room capture, visual editor, live validation, ready-to-send gate | Designers produce jobs that pass the gate and import cleanly |
| 6. AI Design | Design rules, draft generation, decision explanations, review flow | AI drafts pass validation and need only light designer edits on typical jobs |
| 7. Projects & Sales | Customers, quotes, pricing, status tracking | Can run in parallel with Phases 3 to 6, since it depends only on Core and Catalog |
| 8. Optional: Mozaik read-back | Mozaik reader plus manual-entry build sheet | Mozaik jobs can be compared against the master copy |

## 11. Risks, Open Questions, and Next Steps

**Risks**

| Risk | Impact | Mitigation |
|---|---|---|
| ORDX can't carry everything needed (exact placement, certain selections or modifications) | Some items need manual work in Cabinet Vision | Discover early in Phases 0 and 1; flag unsupported items as manual work in the editor |
| Shop catalogs vary widely | Onboarding each shop is slow | Build mapping tools in Phase 4; let AI draft mappings for human review |
| Cabinet Vision applies internal rules not visible in files | Translator behavior hard to predict in some cases | Involve a Cabinet Vision expert; rely on engineered-output verification |
| Vendor licensing or terms restrict this kind of integration | Integration could be limited | Review Cabinet Vision and Cyncly terms; contact both about partner programs before Phase 3 |

**Open questions**

1. Which Cabinet Vision versions do target shops run, and does ORDX behave the same across them?
2. How much room placement and elevation detail does ORDX preserve on import?
3. Which read-back source is most reliable and least fragile: ORDX export, SQL database, or reports?
4. Is there a Cabinet Vision or Cyncly partner program that offers documentation or support?
5. Which internal base unit fits target shops' measurement practices?
6. Which design rules should be blocking versus advisory by default?

**Next steps**

1. Gather 15 to 30 varied completed jobs with ORDX exports and engineered outputs from one shop.
2. Export that shop's Cabinet Vision catalog.
3. Run Phase 0 and Phase 1 and make the go/no-go call before committing to the editor and AI work.
